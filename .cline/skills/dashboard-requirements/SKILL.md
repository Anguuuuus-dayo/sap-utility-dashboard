# /dashboard-requirements — ドラフト → 業務要件書 生成スキル

グループが書いた最小限のドラフト `draft.md` を、**業務物語中心の要件書** `requirements.md`
に増幅する。参加者に構造化（コード・緯度経度・指標定義など）を書かせず、
AI が業務ストーリーとして現実感を持って膨らませるのが狙い。

> **MCP ルール**: このスキルは主にテキスト生成であり、MCP サーバはほぼ使わない。
> CAP/CDS や sap.viz の生成は後続の `/utility-dashboard` が担う。
> MCP サーバは Cline の UI で事前設定済み（`cline_mcp_settings.json`）であることを前提とする。

---

## ワークフロー上の位置づけ

```
1. グループワーク: draft.md を記入                      ← 人
2. /dashboard-requirements : draft.md → requirements.md  ← このスキル
3. /utility-dashboard       : requirements.md → CAP+UI5 一式
4. /chrome-devtools-test    : ブラウザ起動・疎通・スクショ
```

---

## 手順

### 1. ドラフトを読む

プロジェクト直下の `draft.md` を全文読む。

- `draft.md` が無い場合は、同梱の `draft.md` テンプレートを開いて記入するよう案内し、停止する。
- 記入が極端に薄い項目（例: 見たいこと が空）は、テーマから妥当な補完候補を提示しつつ進める。

### 2. 出力見本を確認する

`sample-requirements.md`（発電所ダッシュボードの要件書例）を**書きぶりの手本**として参照する。
- 業務背景 → 利用シーン → 見たい指標 → 画面構成、という流れで物語的に書かれている点を踏襲する。
- ただし**テーマ・業務内容は必ず `draft.md` に従う**こと。見本の発電所ドメインの固定語
  （発電所・JEPX・原子炉 等）をドラフト外のテーマに流用しない。

### 3. 業務要件書に増幅する

ドラフトの各項目を、以下の構成で現実感ある業務ストーリーへ膨らませる。
数値レンジや季節性・拠点規模差などの"現実感"は AI が補ってよい（具体的な採番・緯度経度は書かない）。

1. **シナリオ / 背景** — 誰が、どの業務で、何に困っていて、何を判断したいのか。
2. **対象ユーザーと利用シーン** — ドラフト §2 を具体的なロール・使う場面に展開。
3. **見たいこと（業務要求）** — ドラフト §3 を章立てして、各章に「なぜ見たいか」を添える。
4. **登場する拠点/設備/店舗** — ドラフト §4 を現実感ある顔ぶれに（名前・種類・規模感の違い）。
   具体的なコードや緯度経度は書かず、「10 施設程度／規模に差がある」等の記述に留める。
5. **データの雰囲気** — 期間（月次が前提）・値の大小傾向・季節性など、ドラフト §6 を反映。

### 4. 「今回実装するスコープ」節を必ず付ける（最重要）

後続の `/utility-dashboard` が作れる**部品の手札**に対応づけて、
今回のダッシュボードで作るものを業務語で明示する。**コードや緯度経度は書かない。**

`/utility-dashboard` の手札（選べる部品）:

| 部品 | 向いている用途 |
|---|---|
| KPIカード行 | 重要指標を大きな数字で（当月値・達成率・件数・累計 など） |
| donut | 構成比・内訳（カテゴリ別の割合） |
| line | 時系列推移（月次トレンド） |
| bar | ランキング・拠点別比較（上位5 など） |
| stacked_bar | 内訳つきの時系列（カテゴリ×月の積み上げ） |
| heatmap | 拠点×月のような2軸の濃淡マトリクス |
| map | 拠点の地理分布（ドラフト §5 が「はい」のときのみ） |

スコープ節のフォーマット（例）:

```
## 今回実装するスコープ

- KPIカード: 総利用者数(当月) / 稼働率(当月) / 運営コスト達成率 / 年間累計利用者
- donut: 施設カテゴリ別 利用者構成
- line: 月次 利用者数 推移
- bar: 施設別 運営コスト（上位5）
- heatmap: 施設 × 月 の利用率
- map: 施設マップ（← ドラフトで「はい」の場合のみ）
```

> 広い業務要求のうち、**今回は手札で作れる範囲に絞る**。
> スコープ外にした要求は「将来拡張」として要件書末尾に箇条書きで残してよい
> （`/utility-dashboard` はスコープ節のみを実装対象にする）。

### 5. 書き出してユーザーに提示

生成した要件書を **`requirements.md`**（プロジェクト直下）に書き出す。
既存の `requirements.md` がある場合は上書き確認を取る。

書き出し後、ユーザーに次を提示する:
- 「今回実装するスコープ」節の要約
- 次アクション: 内容を確認し、問題なければ **`/utility-dashboard`** を実行する旨

---

## 出力フォーマット（requirements.md）

```markdown
# <テーマ名> ダッシュボード 要件書

## シナリオ / 背景
...

## 対象ユーザーと利用シーン
...

## 見たいこと（業務要求）
### 1. <章>
...

## 登場する拠点/設備/店舗
...

## データの雰囲気
...

## 今回実装するスコープ
- KPIカード: ...
- donut: ...
- line: ...
（手札から選択）

## 将来拡張（今回は対象外）
- ...
```

## ハードルール

- **テーマ・業務内容は `draft.md` に従う**。見本（`sample-requirements.md`）のドメイン固定語を流用しない。
- **具体的なコード・緯度経度・CSV 行は書かない**。それらは `/utility-dashboard` が §1 で導出する。
- **「今回実装するスコープ」節を必ず含める**。手札（KPIカード/donut/line/bar/stacked_bar/heatmap/map）に対応づける。
- `map` はドラフト §5 が「はい」のときだけスコープに入れる。
